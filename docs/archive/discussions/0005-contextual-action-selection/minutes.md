# コンテキストに応じた Action 選択の議事録

- 日付: 2026-08-29
- 結果: 提案を作成する

## 議論した内容

Target を選択してから、その Target が実行できる Action を選択する段階的な操作へ User Choices を変更する。

Action の候補は、ゲーム全体で解放済みの Action と、選択した Target が実行可能な Action の積集合とする。表示だけを絞り込むのではなく、core の割当処理も未解放または非対応の組み合わせを拒否し、UI とゲームルールの不一致を防ぐ。

選択キーは数字ではなく、表示順に割り当てる `a)`、`b)`、`c)` 形式とする。キーは項目名の頭文字ではなく、現在の選択肢内での位置を表す。選択可能な列だけにキーを表示する。

User Choices は固定した複数列を常時表示しない。Target 選択中は Target だけを表示し、Target が選択された時点で Action 列と区切りを生成する。Action 選択中の Target 列には選択キーを残さず、選択済み Target を区切り直前の `<` で示す。

表示は discovery のサンプルを文字単位で再現する。`> Target:` の空白、Target 名の開始位置、左端の `|`、Action 見出しの `> Action:`、選択済み Target の `<|` を維持する。Target 名の開始位置は Target 選択の前後で変えない。

Action 選択時の Target 列幅は表示内容から動的に計算する。極端に長い Target 名では Action の表示領域を失わないよう、Action に最低20文字分を確保し、必要なら Target 側を切り詰める。

## 確認した質問

1. Action の候補を、解放済み Action と Target が実行可能な Action の積集合にし、core でも制約するか。
2. discovery の `a)` 表記と説明中の数字入力のどちらを採用するか。
3. Target 選択中も将来の列幅と区切りを予約するか、選択に応じて列そのものを生成するか。
4. Action 選択中に Target 側の選択キーを残すか。
5. `>` と見出しの間の空白、Target 名の開始位置、`<` の配置をどの文字位置に置くか。

## 採用しなかった案

- 数字による選択は採用しなかった。選択肢は `a)` から始まる位置ベースの文字キーで表し、数字入力は廃止する。
- 項目名の頭文字をホットキーにする案は採用しなかった。表示順に `a`、`b`、`c` を割り当てるため、項目名の先頭文字が重複しても入力が衝突しない。
- Target、Action、Times の列幅と区切りを常時固定し、未到達の列を空欄にする最初の試作は採用しなかった。選択によって次の選択肢が生まれるという discovery の意図を弱め、サンプルの表示とも一致しなかったためである。
- Action 選択中も Target 側へ `a)` などを表示する案は採用しなかった。現在入力を受け付ける Action だけに選択キーを表示する。
- 選択済み Target の名前直後に `<` を置く案と、Action 列へ向けた `----->` を置く従来表現は採用しなかった。`<` は名前の長さによらず Target–Action 区切りの直前に置く。
- Action 候補を UI だけで絞り込む案は採用しなかった。別のフロントエンドや将来の処理から不正な割当が可能になるため、core の割当処理でも検証する。

## 保留事項

- Action 選択から Target 選択へ戻る専用操作は今回変更しない。現行どおり Action を選ぶと Target 選択へ戻り、`Esc` はゲーム終了として扱う。必要性が生じた場合は別途検討する。
- Times は将来の選択段階として予約するが、機能が実装されるまでは User Choices に表示しない。
